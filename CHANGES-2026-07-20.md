## 1. Delivery-Date Timezone Bug

**The report:** an order placed at 11pm on July 16th, with delivery date explicitly set to July 16th, showed up as **July 17th** in both the admin portal and QuickBooks.

**Root cause:** both the mobile ordering app and the admin portal computed "today" (or the picked delivery date) with the pattern:
```js
date.toISOString().split('T')[0]
```
`toISOString()` always converts to UTC *before* formatting. In any US timezone (all behind UTC), picking a date late at night means the UTC-converted instant has already rolled into the next calendar day by the time its date part gets read — so "today" silently becomes "tomorrow" for anyone ordering late at night.

**Investigation approach:** traced the value from where it's displayed (admin/QuickBooks) backward through the write path — confirmed the backend and QuickBooks push code never touch or reformat the date once it arrives (it's passed straight through as a string), which isolated the bug to the client side. Grepped both codebases for the same anti-pattern rather than fixing just the one reported spot.

**Fix:** a `toLocalDateStr(date)` helper that reads `getFullYear()/getMonth()/getDate()` directly (local time, no UTC conversion), replacing the buggy pattern everywhere it appeared:
- Mobile app: the delivery-date picker and the local order-history timestamp (`OrderApp/components/ShoppingCart.js`)
- Admin portal: 5 separate occurrences — packing-report default date, QB invoice-pull date range, the "today's orders" stat, and two new-product invoice-start-date defaults (`backend/public/index.html`)

**Interview angle:** good example of not stopping at the one reported symptom — the same bug existed in 5 other places once I knew the pattern to look for, and fixing all of them from one root-cause understanding is cheaper than fixing them one bug report at a time.

## 2. Order History: Date-Range Filtering + UI Redesign

**The ask:** replace the fixed "last 3 days" order view with selectable ranges (Today / 3 Days / Week / Month, past or future), and replace the card-grid UI (click a card → modal popup) with an expandable list (click a row → expands in place).

**Backend change:** `GET /api/orders` gained `?from=&to=` query params for an explicit date range, alongside the pre-existing default (rolling 3 days) and `?date=` (single day) — fully backward compatible, since every existing caller used the no-params default.

**A design conflict I had to flag before building:** the app already hard-deletes orders older than 3 days on a nightly job (by original design — flat, short-lived order history). Adding a "past month" filter option would be pointless if the underlying data was already gone. Raised this explicitly rather than silently building a filter that wouldn't work — the retention window was extended from 3 days to **31 days** (1 day of buffer past the 30-day "month" filter) as a result.

**Frontend change:** replaced the `.order-grid`/`.order-card` + modal pattern with an accordion-style list — click a row, it expands in place and lazy-loads full order detail (cached after first load so re-expanding doesn't re-fetch). Removed the now-dead modal markup and its handler functions rather than leaving them as unused dead code.

**Verification:** rather than trusting it by inspection, spun up the backend locally, created a real test order via the API, confirmed it appeared under a "today" range query and *not* under a "yesterday" range query, fetched its full detail through the same endpoint the accordion uses, deleted it, and confirmed inventory was correctly restored and the order fully gone — a real end-to-end pass, not just "the code looks right."

**Interview angle:** the retention-window conflict is a good example of catching a requirements gap before writing code that would ship broken, and negotiating the actual constraint (why 3 days existed) rather than just doing what was asked literally.

## 3. Production Reliability Bug: Unhandled Async Errors Crashing the Whole Backend

This was **not** something I was asked to look for — I found it by accident while verifying the work above, and it turned out to be the most significant thing fixed today.

**What happened:** while testing the new order-range endpoints, a malformed request (`GET /api/orders/undefined`, from a bug in my own test script) caused a Postgres type-cast error inside the `getOrder` controller. The entire Node process **crashed and exited** — not just that one request failing, the whole server went down. I reproduced this a second time, independently, with an unrelated schema mismatch during order creation.

**Root cause:** Express 4 (what this app runs) only automatically catches *synchronous* throws inside route handlers and forwards them to the app's central error-handling middleware. Nearly every controller in this codebase is written as `async function` with bare `await pool.query(...)` calls and no try/catch — when one of those rejects, Express has no way to see it, since it never attaches a `.catch()` to what an async handler returns. The rejection becomes an **unhandled Promise rejection** at the process level, and Node 15+ treats that as fatal by default: the process exits immediately.

**Why this matters beyond "a bug was fixed":** this means *any* single bad request, or any transient database hiccup, anywhere across ~11 controllers, could take the entire backend offline for every customer and admin simultaneously — not a degraded single request, a full outage — until Railway's process supervisor restarted it. This is the kind of bug that, in production, looks like unexplained brief full-site outages that don't obviously trace back to "someone hit a malformed URL."

**Fix:**
- `express-async-errors` — a single `require()` that patches Express to route rejected Promises from async handlers into the existing error middleware (clean `500` response) instead of letting them escape as unhandled rejections. Chosen over manually wrapping all ~11 controllers' routes individually, since a global patch means no route can be missed by oversight later.
- While in there, found and fixed one more instance of the same root problem outside the request cycle entirely: the nightly `purgeOldOrders()` background job was invoked with no `.catch()` at all.
- Added `process.on('unhandledRejection'/'uncaughtException', ...)` as a last-resort net — logs and keeps the process alive rather than crashing, for anything that might still slip past the above.

**Verification, not just theory:** restarted the backend and replayed the *exact* malformed request that had crashed it earlier. Confirmed it now returns a clean `500` and — critically — that the process was still alive and answering `/api/health` immediately afterward, where before it had exited entirely.

**Interview angle:** this is the strongest story of the day — a real production-reliability class of bug (not a feature bug), found through disciplined verification rather than code review, root-caused to a specific framework/runtime interaction (Express 4's async handling + Node's unhandled-rejection default), fixed with a minimal and low-risk change, and proven fixed by reproducing the original failure rather than just asserting the fix "should work."
