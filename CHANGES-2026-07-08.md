# Seven Stars Food — Changes Summary (2026-07-08)

---

## 1. QB Webhook Item Sync — `unit` NOT NULL Crash
**Problem:** `webhooksController.js`'s `syncItem()` inserted new products from QB Item webhooks without setting `unit` (`NOT NULL` column). Any item created **directly in QuickBooks** (not via the admin portal) failed on every retry:
```
Webhook processing error: null value in column "unit" of relation "products" violates not-null constraint
```
**Fix:** Extracted the matching/upsert logic that `syncController.js`'s manual "Sync from QB" already did correctly (link an existing local product by SKU if one exists with no `qb_item_id` yet; default `unit` to the QB item's `UnitOfMeasure`, falling back to `'ea'`) into a shared helper, and pointed the webhook path at it instead of its own broken copy.

**Files:** `backend/src/services/qbEntitySync.js` (new), `backend/src/controllers/webhooksController.js`

---

## 2. Mobile Order → QB Push — Duplicate Key on `customers_qb_customer_id_key`
**Problem:** `mobile.js` had its own forked copy of `pushToQB()`, missing the "is this `qb_customer_id` already claimed by another local row?" guard that `ordersController.js`'s copy has. When two local customer rows resolved to the same QB company (duplicate/unmerged customer record), the unguarded `UPDATE customers SET qb_customer_id = ...` collided with the unique constraint and the invoice push was dropped silently:
```
Found existing QB customer 323 for "AA SUSHI"
QB invoice push failed for mobile order: duplicate key value violates unique constraint "customers_qb_customer_id_key"
```
**Fix:** Deleted the duplicate implementation in `mobile.js`; it now calls the single guarded `pushToQB` exported from `ordersController.js`.

**Files:** `backend/src/controllers/ordersController.js`, `backend/src/routes/mobile.js`

---

## 3. QB Invoice Numbers Didn't Match What's Shown in QuickBooks
**Problem:** Two separate issues in `qbSync.js`:
- We only ever stored QB's internal `Id` (e.g. `56759`) as `qb_invoice_id`. QuickBooks Online displays invoices by `DocNumber` (a different value), so "invoice 56759" in our logs/DB meant nothing to someone looking at QBO.
- `createQBInvoice()` also computed its own `DocNumber` client-side (`SELECT DocNumber FROM Invoice ORDERBY Id DESC` + 1) and forced it onto new invoices — racy under concurrent order creation (two invoices created close together could compute the same "next" number).

**First attempt (wrong):** Removed the custom numbering entirely, assuming QBO would auto-assign `DocNumber`. It didn't — a diagnostic (`backend/scripts/check-qb-doc-number.js`) confirmed this QBO company has **"Custom transaction numbers" enabled**, which means QBO leaves `DocNumber` blank unless the caller supplies one. Invoices created during the window this was deployed have no invoice number in QBO at all (ids 56763, 56765 confirmed blank — need manual backfill in the QBO UI).

**Real fix:** Custom numbering is required for this company, so it's back — but sourced from a new Postgres sequence (`qb_invoice_doc_number_seq`, migration `010_qb_doc_number_seq.sql`) instead of reading QBO's last DocNumber, which is atomic under concurrent order creation instead of racy. `ordersController.js`'s `createQBInvoiceWithDocNumber()` draws the next value and retries (up to 3x) if QBO rejects it as a duplicate (error code 6140 — e.g. a staff member created an invoice directly in QBO with the same number around the same time). Also added an `orders.qb_doc_number` column and now store/log QBO's actual `DocNumber` everywhere an invoice is created or merged, alongside the internal `Id`.

**Files:** `backend/src/middleware/qbSync.js`, `backend/src/controllers/ordersController.js`, `backend/src/controllers/webhooksController.js`, `backend/migrations/009_qb_doc_number.sql`, `backend/migrations/010_qb_doc_number_seq.sql` (both applied to local dev DB)

## 4. QB "Sync from QB" — Only Report Real Changes
**Problem:** The admin "Sync from QB" button (`upsertItems`/`upsertCustomers` in `syncController.js`) unconditionally ran an `UPDATE` (bumping `updated_at`) and counted every item/customer toward `items_synced`/`customers_synced`, even when nothing had actually changed — no way to tell what a sync run really did.
**Fix:** The shared `upsertQBItem`/`upsertQBCustomer` helpers (see #1) now diff incoming QB data against the existing row field-by-field, skip the write entirely if nothing differs, and return the specific changed fields (`{ field: { from, to } }`) when something does. `POST /api/admin/sync-from-qb` now responds with `created` / `updated` / `unchanged` counts plus an itemized `changes` list (product/customer name + exactly which fields changed), and only logs entries that actually changed.

**Files:** `backend/src/services/qbEntitySync.js`, `backend/src/controllers/syncController.js`

## Insights / Notes
- **Root pattern behind bugs #1 and #2:** `mobile.js` and `ordersController.js` had each grown their own near-identical copy of QB push/sync logic over time. Both copies drifted — one had a bug fix the other didn't. Worth checking for other duplicated logic between these two files before it bites again.
- **`Seven-Stars-App/Seven Star Food LLC/` directory:** a merge commit (`8ae2e6d`, "merge conflict") accidentally pulled in an unrelated native Xcode/Swift project plus a duplicate copy of `OrderApp` into the repo root (~9MB, 57 files). Not the cause of any bug fixed today, but it's tracked in git and should be removed or confirmed intentional with whoever it belongs to.
- **`npx expo start` hanging/slow:** unrelated to any of the above — caused by running the command from the repo root instead of `OrderApp/` (no local `expo` binary there, so npx tried to download a fresh, newer `expo` package and hit a corrupted npx cache). Fixed by clearing `~/.npm/_npx/...` and always running `npm start` / `npx expo start` from inside `OrderApp/`.
